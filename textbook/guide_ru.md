# Knowledge Bundles for AI Agents
# Наборы знаний для агентов искусственного интеллекта

### A practical guide to OKF and agent-ready codebases
### Практическое руководство по OKF и кодовым базам, готовым к внедрению агентов

## Preface
## Предисловие

Эта книга — о том, как подготовить кодовую базу к работе с AI-агентом.
Не о промптах, не о моделях, не о «как заставить LLM писать код». А о
том, **что положить рядом с кодом**, чтобы агент работал эффективно.

Основная проблема, с которой сталкивается каждая команда, внедряющая
агентов, звучит так:

> «Агент не понимает наш проект. Он каждый раз задаёт одни и те же
> вопросы, забывает, что мы уже обсуждали, и путается в контексте.»

Причина не в модели. Причина в том, что **знания о проекте не
структурированы**. Всё лежит либо в головах разработчиков, либо в одном
гигантском `AGENTS.md`, который агент читает целиком, но не понимает.

Эта книга предлагает решение: **локальный knowledge bundle** —
директорию с markdown-файлами, каждый из которых описывает одну тему,
и которые загружаются агентом по требованию.

Подход основан на **[Open Knowledge Format (OKF)](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing)** — открытом стандарте от Google Cloud для представления знаний в виде markdown-файлов с
YAML frontmatter.

### Для кого эта книга

- **Разработчики**, которые работают с [OpenCode](https://opencode.ai), [Claude Code](https://claude.com/product/claude-code), [Cursor](https://cursor.com)
  или другими агентами и хотят повысить качество их ответов
- **Тимлиды**, которые внедряют агентов в команду и хотят стандартизировать
  работу с контекстом
- **Архитекторы**, которым интересно, как устроены knowledge bundles
  и почему [OKF](https://cloud.google.com/blog/products/data-analytics/okf-v0-2-adds-trust-signals) выбран как фундамент
- **Все, кому надоело** раздувать `AGENTS.md` до 500 строк

### Как читать

Книга линейная, но её можно читать по частям:

- **Part I (Foundations/Основы)** — обязательно для всех. Объясняет, зачем

Если вы новичок — начните с Part I, потом Part III, потом возвращайтесь

### Что нужно знать заранее

- [Markdown](https://www.markdownguide.org) на базовом уровне
- Понимание, что такое [YAML frontmatter](https://docs.github.com/en/contributing/writing-for-github-docs/using-yaml-frontmatter) (Jekyll, Hugo, Obsidian — не

## Chapter 1. The problem: why agents drown in context
## Глава 1.  Проблема: почему агенты тонут в контексте

### 1.1 Как выглядит типичный AGENTS.md

Откройте любой репозиторий, где разработчики уже пользуются AI-агентами.
Скорее всего, вы увидите файл `AGENTS.md` (или `CLAUDE.md`, или
`.cursor/rules/`) примерно такого содержания:

```markdown
# Project: acme-billing

## Overview
ACME Billing — SaaS для выставления счетов. Rails 7.1, PostgreSQL 16,
Redis, Sidekiq. Multi-tenant, около 200 000 активных пользователей.

## Architecture
Основные компоненты:
- `InvoiceGenerator` — генерирует счета
- `PaymentGateway` — интеграция со Stripe
- `SubscriptionManager` — управляет подписками
- `NotificationService` — email и push
- `ReportBuilder` — отчёты
- ...

## Code Style
- RuboCop с конфигом `.rubocop.yml`
- Все файлы начинаются с `# frozen_string_literal: true`
- SPDX headers в каждом файле
- ...

## CI
У нас 5 GitHub Actions:
1. test.yml — RSpec
2. lint.yml — RuboCop
3. build.yml — Docker image
4. deploy-staging.yml
5. deploy-prod.yml
...

## Key Files
| File | Purpose |
|------|---------|
| app/models/invoice.rb | Invoice model |
| app/services/invoice_generator.rb | Generates invoices |
| ...
(50 more rows)

## Testing
- RSpec
- FactoryBot
- VCR для внешних API
- ...

## Deployment
- Staging: auto on push to master
- Prod: manual, tags v*
- Rollback: kubectl rollout undo
- ...

## Security
- Secrets в AWS Secrets Manager
- Never commit .env
- ...

## FAQ
- Q: How do I reset the DB?
- A: bundle exec rails db:reset
- ...
```

Файл разросся до 500–600 строк. Кажется, что он **полный** — в нём
есть всё, что нужно знать о проекте.

Но вот что происходит, когда вы просите агента:

> «Добавь поле `discount` в Invoice»

Агент получает **весь** этот файл в контекст, 600 строк. Из них
релевантны: строчка про `Invoice` в Key Files; code style (для
правильного синтаксиса); тесты. Всё остальное — CI-таблицы,
deployment, security, FAQ — **шум**.

### 1.2 Три проблемы раздутого AGENTS.md

**Проблема 1: шум**

Агент тратит контекстное окно на нерелевантную информацию. Чем больше
шума, тем меньше места остаётся для самой задачи. У моделей есть предел —
и чем ближе к нему, тем хуже качество ответов.

**Проблема 2: размытое внимание**

Даже если контекстное окно большое, модель **теряет фокус** на длинном
вводе. Информация в середине файла обрабатывается хуже, чем в начале
и конце (эффект «lost in the middle»). Строчка про `Invoice` в
середине 600-строчного файла может быть проигнорирована.

**Проблема 3: устаревание**

Один большой файл трудно поддерживать. Каждый раз, когда меняется **CI
workflow**, нужно лезть в середину `AGENTS.md`. Когда меняется архитектура —
в другую секцию. Через полгода половина файла устарела, но никто не
знает, какая именно.

### 1.3 Почему это происходит

Разработчики кладут в `AGENTS.md` всё подряд по одной простой причине:
_**они не знают, что попадёт в контекст агента в следующий раз**_

Если агент читает `AGENTS.md` целиком и всегда — соблазн положить туда
всё, чтобы «на всякий случай было». Логика: _«пусть лучше будет, чем не
будет»_.

Проблема в том, что _«пусть будет»_ работает против агента. Он **не может
игнорировать** то, что уже в контексте. Он вынужден обрабатывать всё,
включая нерелевантное.

### 1.4 Что если разбить на файлы?

Очевидная идея: вместо одного большого `AGENTS.md` сделать несколько
маленьких файлов — по темам.

```
.opencode/
├── architecture.md
├── code-style.md
├── ci.md
├── deployment.md
└── ...
```

Но эта идея без правил превращается в новый хаос:

- Как агент узнаёт, **какой** файл читать?
- Как понять, что в файле **актуально**?
- Что если один файл ссылается на другой, а тот — на третий?
- Как обновлять файлы, чтобы они не разъезжались?
- Как понять, что в файле **есть**, не читая его целиком?

Нужна **система**. Не просто «разбить на файлы», а **формат**, который
описывает:

1. Как файлы устроены (_frontmatter_)
2. Как они связаны (_links_)
3. Как понять содержимое без полного чтения (_type_, _description_)
4. Как вести файлы, чтобы они не устаревали (_boundaries_, _rules_)

Такая система существует. Она называется **[Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing)**

### 1.5 Идея: lazy loading

Решение проблемы раздутого `AGENTS.md` — **ленивая загрузка**

Вместо того чтобы читать всё сразу, агент:

1. Читает **только** `AGENTS.md` — маленький файл с ядром
2. В `AGENTS.md` — таблица: «если задача X, читай файл Y»
3. Когда приходит задача, агент смотрит в таблицу и читает **только
   нужный** файл

Пример:

```markdown
## Reference files

| File | When to read |
|------|-------------|
| _architecture.md | Architecture, components, data flow |
| _ci.md | CI failed |
| _codestyle.md | Writing code |
| _troubleshooting.md | Local environment broken |
```

Задача «добавь поле в Invoice» → агент читает `AGENTS.md` (маленький)
+ `_codestyle.md` (для синтаксиса) + `_files.md` (где Invoice) +
`_concepts.md` (архитектура). 4 файла, каждый по теме. Никаких CI-таблиц,
deployment или security FAQ

Задача «CI упал» → агент читает `AGENTS.md` + `_ci.md`, это два файла.

**Результат:** агент всегда читает **только то, что нужно** для
текущей задачи, контекст не засоряется.

## Chapter 2. What OKF is
## Глава 2. Что это такое OKF ?

### 2.1 Определение

**Open Knowledge Format (OKF)** — открытый формат от Google Cloud для
представления знаний в виде markdown-файлов.

Официальная спецификация:
[SPEC.md](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md).

Ключевая идея, прямо из спеки:

> OKF takes the position that knowledge is best represented in commonly
> accessible, established formats that are:
>
> - Readable by humans without tooling
> - Parseable by agents without bespoke SDKs
> - Diffable in version control
> - Portable across tools, organizations, and time

> OKF придерживается позиции, что знания лучше всего представлять в 
> общедоступных , устоявшихся форматах, которые:
> 
> - Читается людьми без использования инструментов
> - Может анализироваться агентами без специальных SDK
> - Может изменяться в системе управления версиями 
> - Переносимость между различными инструментами, организациями и временем

То есть: **знания должны быть в формате, который читается и человеком,
и машиной, без специальных инструментов**

### 2.2 Четыре принципа OKF

Из цитаты выше вытекают четыре принципа.

**Принцип 1: читаемость человеком**

`cat file.md` — и вы видите содержимое. Никаких бинарных форматов, никакой
base64, никаких сжатых архивов, только текст.

**Принцип 2: парсимость агентом**

Структура достаточно формальна, чтобы её распарсил любой агент. YAML
frontmatter, markdown body, ссылки. Никаких «кастомных SDK», чтобы
прочитать.

**Принцип 3: diffable в git**

Изменения видны в `git diff`. Не «файл изменился целиком», а «строка 42
изменилась». Это критично для командной работы и ревью.

**Принцип 4: портативность**

Знание живёт вне конкретного инструмента. Вы можете открыть файл в
любом редакторе, закоммитить в git, передать коллеге — и всё работает.

### 2.3 Минимализм как философия

OKF подчёркивает **минимализм**:

> No central schema registry, no mandatory tooling. If you can `cat` a
> file, you can read OKF. If you can `git clone`, you can distribute it.

> Нет центрального реестра схем, нет обязательных инструментов. Если вы 
> можете выполнить для файла `cat`, вы можете прочитать OKF. 
> Если вы можете выполнить команду `git clone`, вы можете распространять его.

Три следствия:

1. **Нет реестра схем** Вы не регистрируете свои типы в каком-то
   центральном месте. Хотите новый тип —  просто придумываете, используете.
2. **Нет обязательного инструментария** Нет CLI, который «надо
   установить». Нет парсера, без которого «не работает».
3. **Читается через cat** Если файл выглядит как текст — он OKF.

Это радикально отличается от XML-схем (XSD), Protobuf, OpenAPI, где
нужен генератор, парсер, валидатор. OKF говорит: «всё это — overkill
для знаний о проекте».

### 2.4 Что OKF описывает

OKF описывает **структуру bundle** — директории с концептами.

```
bundle/
├── index.md           # оглавление
├── log.md             # история изменений
├── concept-a.md       # концепт
├── concept-b.md
└── subdirectory/
    ├── index.md
    └── concept-c.md
```

**Концепт** — это markdown-файл с двумя частями:

1. **YAML frontmatter** — метаданные
2. **Body** — содержимое

### 2.5 Frontmatter

Frontmatter — блок между двумя `---` в начале файла:

```yaml
---
type: <Type name>                  # REQUIRED
title: <Optional display name>
description: <Optional one-line summary>
resource: <Optional canonical URI>
tags: [<tag>, <tag>]
timestamp: <ISO 8601 datetime>
---
```

**Обязательное поле — одно: `type`**

Это строка, которая говорит, **что за концепт** перед нами.
`project-context`, `architecture`, `ci`, `finding`, `runbook` — всё что
угодно. OKF не регистрирует значения, вы сами решаете.

**Почему `type` обязателен:**

Потому что агент может **не читать тело файла**, чтобы понять, о чём
он. Увидел `type: ci` — понял: это про CI. Увидел `type: finding` —
это находка анализа, можно пропустить, если задача не про анализ.

**Остальные поля — recommended:**

- `title` — человекочитаемое имя
- `description` — одно предложение для описания содержимого
- `resource` — канонический URI ресурса
- `tags` — категории
- `timestamp` — когда файл менялся

**Расширения:**

Спека явно говорит: производители могут добавлять **любые**
дополнительные ключи. Потребители **должны** толерантно их обрабатывать.

Это значит: если вы придумали поле `severity: high` — используйте, OKF не падает.

### 2.6 Body

Body — обычный markdown. Никаких ограничений на структуру.

Но спека **рекомендует** структурный markdown (заголовки, списки,
таблицы, блоки кода) вместо свободного текста. Почему: структура
помогает и чтению человеком, и извлечению агентом.

OKF описывает **конвенциональные секции** — но они не обязательны:

| Заголовок | Назначение |
|-----------|-----------|
| `# Schema` | Структурированное описание полей |
| `# Examples` | Примеры использования |
| `# Citations` | Внешние источники |

Вы можете использовать их или нет. Если используете — они узнаваемы.

### 2.7 Cross-linking

Ссылки между концептами — обычные markdown-ссылки. Две формы:

**Абсолютные (от корня bundle):**

```markdown
See [customers table](/tables/customers.md)
```

Стабильны при перемещении файлов

**Относительные:**

```markdown
See [neighboring concept](./other.md)
```

OKF **рекомендует абсолютные** — они работают независимо от положения
файла в директории, но относительные тоже допустимы.

**Семантика ссылок:** ссылка от A к B утверждает **наличие
отношения**. Тип отношения — определяет окружающий текст. «См. ADR-005»
и «См. `_decisions.md`» — разные отношения, но синтаксис один.

**Битые ссылки — допустимы** OKF говорит: потребители должны
толерантно относиться к битым ссылкам. Возможно, это просто ещё не
написанное знание.

### 2.8 Conformance - надо буде добавить данные по v0.2 !!!!

Bundle соответствует OKF v0.1 если:

1. Каждый `.md` файл (кроме `index.md`, `log.md`) содержит парсируемый
   YAML frontmatter
2. Каждый frontmatter содержит непустое поле `type`
3. `index.md` и `log.md` следуют описанной структуре

**Но!** Потребители **не должны** отвергать bundle из-за:

- Отсутствия опциональных полей frontmatter
- Неизвестных значений `type`
- Неизвестных дополнительных ключей frontmatter
- Битых cross-ссылок
- Отсутствующих `index.md`

Это **сознательное решение**. OKF должен оставаться полезным по мере
роста, рефакторинга и частичной генерации агентами.

То есть: строгий OKF-конформный bundle — редкость. И это **нормально**.
OKF — это ориентир, не догма.

### 2.9 Что OKF не делает

OKF — это **формат**, а не **методология**. Он не говорит:

- Какие типы концептов должны быть
- Как организовывать bundle
- Как агент должен его читать
- Как обновлять файлы

Всё это — уровень приложения. OKF только описывает **форму**, в
которую вы кладёте знания.

Именно здесь начинается наш шаблон — он берёт OKF как фундамент и
добавляет поверх методологию работы с AI-агентом.

## Chapter 3. The bundle as a unit of knowledge
## Глава 3.  Комплект как единица знания

### 3.1 Определение

**Bundle** — это **директория с markdown-концептами**, организованная
по правилам OKF.

Bundle — **не файл**, не **несколько файлов**, а **директория целиком**
**bundle (комплект знаний)** представляет собой **обычную директорию (папку) на диске**, которая объединяет связанные файлы документации и метаданных
По сути, **bundle**— это единица дистрибуции знаний (по аналогии с репозиторием или вики-системой), оформленная в виде графа взаимосвязанных концептов. Любой ИИ-агент или поисковый робот может прочитать этот пакет, понять структуру компании, баз данных или API и использовать информацию без галлюцинаций

```
bundle/
├── index.md
├── log.md
├── concept-a.md
├── concept-b.md
└── subdirectory/
    ├── index.md
    └── concept-c.md
```

Всё, что лежит внутри — часть bundle. Всё, что снаружи — не часть.

### 3.2 Bundle в нашем шаблоне

В нашем шаблоне bundle — это директория **`.opencode/`** в корне проекта.

```
my-project/
├── .opencode/          ← ← ← bundle
│   ├── AGENTS.md
│   ├── _concepts.md
│   ├── _setup.md
│   └── ...
├── src/
├── tests/
└── README.md
```

Обратите внимание: bundle **отделена** от кода проекта. Она живёт в
своей директории, не пересекается с `src/`, `tests/`, `docs/`.

### 3.3 Почему именно директория

Могли бы быть варианты:

- **Один файл** `AGENTS.md` со всем содержимым. Именно от этого мы
  уходим.
- **Несколько файлов в корне** `AGENTS.md`, `CONCEPTS.md`, `CI.md` в
  корне проекта, всё это загрязняет репозиторий.
- **Директория в корне** `docs/` или `knowledge/`. Смешивается с
  публичной документацией.
- **Директория `.opencode/`**  - Наш выбор.

**Почему `.opencode/`:**

1. **Изолирована** Не мешает другим файлам
2. **Не коммитится** По умолчанию в `.git/info/exclude`
3. **Именована по инструменту** Понятно, что это для OpenCode
4. **Расширяема** Можно добавить поддиректории

### 3.4 Bundle — это замкнутый мир

Bundle — **самодостаточен**
Внутри — все знания о проекте, нужные агенту

Это не значит, что bundle **полный**. Он не содержит весь код, всю
документацию, всю историю. Он содержит **карту** — как ориентироваться
в проекте.

**Аналогия:** bundle — как путеводитель по городу, а не сам город. Это
карта + описания. По путеводителю вы понимаете, куда идти, но сам
город — отдельно.

### 3.5 Bundle vs repository

Не путать:

| Bundle | Repository |
|--------|-----------|
| Директория `.opencode/` | Весь git-репозиторий |
| Знания о проекте | Код + история + issues + PR |
| Не коммитится | Коммитится |
| Локальный | Распространяется |
| Изменяется вами | Изменяется командой |
| Один на проект | Один на проект |

Bundle — **часть** проекта, но не часть **репозитория**. Он рядом, но
снаружи.

### 3.6 Bundle vs template

Ещё одно различие:

| Bundle | Template |
|--------|----------|
| То, что **есть** в проекте | То, что **копируется** |
| Уникален для проекта | Одинаков для всех |
| `.opencode/` | `template/` в репозитории шаблонов |
| Заполняется под проект | Содержит плейсхолдеры |
| Результат | Источник |

Шаблон — это «формочка», а bundle — «выпечка». Из одной формочки
получается много bundle'ов.

### 3.7 Bundle vs codebase

И ещё одно:

| Bundle | Codebase |
|--------|----------|
| `.opencode/` | `src/`, `lib/`, `app/` |
| Знания **о** коде | Сам код |
| Markdown | Любой язык |
| Не компилируется | Компилируется |
| Читается агентом | Читается компилятором |

Bundle — **не код**, а bundle — это **о коде**.

### 3.8 Почему bundle, а не collection / package / library

Вопрос терминологии. Мы обсуждали это в контексте OKF, но стоит
повторить.

| Слово | Почему не оно |
|-------|---------------|
| **Collection** | Слишком общее, нет структуры |
| **Package** | Ассоциируется с npm, pip — а не с знаниями |
| **Library** | Ассоциируется с кодом |
| **Repository** | Сильно связан с git |
| **Directory** | Технически, без семантики знания |
| **Bundle** | Нейтральное, есть метафора связки |

**Bundle** — официальный термин OKF. Google выбрал его, и мы следуем.

### 3.9 Анатомия bundle

Минимальный OKF-конформный bundle:

```
bundle/
├── index.md           # оглавление
└── log.md             # история
```

Всё, и больше ничего **не обязательно**.

Но минимальный bundle **бесполезен**, в нём нет знаний.

Наш bundle расширен:

```
.opencode/
├── index.md           # OKF entry
├── log.md             # OKF log pointer
├── AGENTS.md          # главный файл
├── SPEC_REFERENCE.md  # выдержка из OKF
├── _*.md              # reference files
├── issue/             # динамические
├── playbook/
├── pr/
├── analysis/
├── runbooks/
└── archive/
```

Расширения мы рассмотрим в следующих главах.

### 3.10 Bundle — не догма

Важно: bundle — **не обязательно** `.opencode/`. Вы можете назвать
директорию иначе, если хотите. Можете добавить свои поддиректории, но для удобства и ясности директорию называют по имени Агента.

OKF не диктует имена, он диктует **правила** (frontmatter, type,
cross-linking), но не **названия**.

Наш выбор `.opencode/` — конвенция **этого шаблона**, не OKF.

## Chapter 4. Lazy loading
## Глава 4. Ленивая загрузка информации

### 4.1 Идея

**Lazy loading** — загрузка по требованию. Противоположность —
**eager loading** (загрузить всё сразу).

- **Eager:** агент читает все файлы bundle при старте.
- **Lazy:** агент читает только тот файл, который нужен для задачи.

Мы используем **lazy**. Почему — всё объяснение ниже.

### 4.2 Eager loading: почему плохо

Представьте bundle с 20 файлами по 100 строк каждый. Итого — 2000
строк.

**Eager loading** — агент читает все 20 файлов при старте. 2000 строк
в контексте.

Проблемы:

1. **Контекстное окно** - У моделей есть предел, 2000 строк — это уже
   заметная часть. Чем ближе к пределу, тем хуже ответы.
2. **Стоимость** - Каждый токен стоит денег (или латентности). Читать
   2000 строк ради задачи, где нужны 200 — wasteful.
3. **Потеря фокуса** - На длинном вводе модель теряет внимание к
   деталям. Ключевая информация в середине 2000 строк может быть
   проигнорирована.
4. **Время старта** - Прежде чем ответить, агент тратит время на чтение
   всего, даже если задача простая.

### 4.3 Lazy loading: как работает

**Lazy loading** — агент читает **только** то, что нужно для задачи.

Механизм:

1. Агент получает **точку входа** — `AGENTS.md`, маленький файл
   (~60 строк)
2. В `AGENTS.md` — таблица: «если задача X → читай файл Y»
3. Агент смотрит на задачу, определяет X, читает Y
4. Работает

Пример из `AGENTS.md`:

```markdown
## Reference files (lazy-loaded)

| File | When to read |
|------|-------------|
| _concepts.md | Architecture, key patterns, data flow |
| _setup.md | Getting the project running locally |
| _codestyle.md | Writing code — SPDX, lint, conventions |
| _ci.md | CI fails — workflows and common failures |
| _troubleshooting.md | Local env broken — non-CI problems |
```

**Задача:** «Добавь метод в класс User»

**Что делает агент:**

1. Читает `AGENTS.md` - Видит таблицу
2. Понимает: задача — про написание кода. Нужен `_codestyle.md`
3. Также нужен `_concepts.md` — понять, где находится `User`
4. Может быть, `_files.md` — узнать, в каком файле `User`
5. Читает 3 файла, **НЕ** 20 !!

**Задача:** «CI красный»

**Что делает агент:**

1. Читает `AGENTS.md`
2. Понимает: задача — про CI. Нужен `_ci.md`
3. Читает 1 файл, **Не 20** !!

### 4.4 Триггеры чтения

Ключевой элемент lazy loading — **колонка «When to read»** в таблице

Формулировка триггера важна. Она должна быть:

- **От задачи, не от файла** - Не «Что внутри: architecture», а «When to
  read: architecture, key patterns, data flow». Агент ищет по ситуации.
- **Однозначной** - «When to read: writing code» лучше, чем «When to
  read: sometimes useful»
- **Конкретной** - «CI fails» лучше, чем «problems»

Правило: **если вы не можете сформулировать, когда читать файл — файл,
возможно, не нужен**

### 4.5 Проблема: как агент определяет, что читать

Агент **не читает все файлы подряд** и не запускает поиск по содержимому
Он опирается на:

1. **Таблицу в `AGENTS.md`** - Основной механизм
2. **Frontmatter файлов** `type`, `title`, `description`. Агент может
   быстро просмотреть метаданные, не читая тела.
3. **Собственное суждение** - Модель достаточно умна, чтобы понять:
   «задача про X, файл `_x.md` описывает X»

Это работает благодаря **человеко-читаемой природе** OKF. Файлы — не
бинарные, не закодированные. Их метаданные явны.

### 4.6 Что если агент ошибается

Иногда агент выбирает **не тот** файл. Причины:

- Триггер сформулирован размыто
- Задача неоднозначна
- Модель ошиблась

Решения:

1. **Уточните задачу** - «Расскажи про архитектуру» лучше, чем «расскажи
   про проект»
2. **Уточните триггеры** - Если агент часто ищет не там — переформулируйте
   «When to read»
3. **Скажите прямо** - «Прочитай `_concepts.md` и объясни X». Агент
   прочитает.

**Это не баг, а фича** Мы сознательно не заставляем агента читать
всё — ценой того, что иногда он ошибается. Цена ошибки — один лишний
запрос. Цена eager loading — **всегда зашумлённый контекст**.

### 4.7 Lazy loading и человека

Ленивая загрузка работает не только для агента, но и для **вас**

Когда вы работаете с проектом, вы тоже не читаете всё сразу. Вы
открываете нужный файл — `_concepts.md`, `_setup.md`, что угодно.

Bundle — **двухуровневый инструмент**:

- Человек читает файлы вручную, по мере необходимости
- Агент читает файлы лениво, по триггерам

Оба выигрывают от структуры

### 4.8 Lazy loading vs grep

Лёгкое возражение: «Почему бы агенту не искать по grep, вместо
таблицы?»

Причины:

1. **Grep ищет по словам, а не по смыслу** - Задача «напиши код» не
   содержит слова «codestyle» или «SPDX». Grep не найдёт.
2. **Grep не понимает структуру** - Он найдёт `_codestyle.md`, но не
   поймёт, что это про стиль
3. **Таблица — это явное знание** - Grep — догадки. Таблица — карта.

Таблица в `AGENTS.md` — это **явное** описание того, что когда читать.
Grep — это **неявный** поиск. Первое надёжнее.

### 4.9 Lazy loading — не только про токены

Экономия токенов — не единственная цель. Есть ещё:

1. **Точность** - Агент получает **только релевантный** контекст. Меньше
   шума — точнее ответ.
2. **Скорость** - Читать 3 файла быстрее, чем 20.
3. **Стоимость** - Меньше токенов — дешевле.
4. **Масштабируемость** - Bundle может расти без ухудшения качества.
   Добавили 5 новых файлов — агент их читает только когда нужно.
5. **Ясность для человека**  - Каждый файл имеет одно назначение. Легко
   найти нужное.

### 4.10 Пределы lazy loading

Lazy loading работает **не всегда**.
Ограничения:

1. **Таблица должна быть точной** - Если триггеры размыты — агент
   ошибается
2. **Модель должна уметь «рассуждать»** - Очень слабые модели могут не
   понять триггеры
3. **Задачи должны быть разделимы** - Если задача про **всё сразу** —
   lazy loading не помогает
4. **Файлы не должны ссылаться друг на друга в цикле** - Иначе агент
   читает всё подряд

Все эти ограничения — решаемые. Но важно понимать, что lazy loading —
**инструмент**, не волшебство.
